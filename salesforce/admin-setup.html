📋 Prerequisites & Licensing

Salesforce Edition Requirements

Agentforce is available on the following editions (as of early 2026):

  • Enterprise Edition: Base platform; Agentforce available as an add-on license.
  • Unlimited Edition: Includes Agentforce capabilities — check your contract for conversation limits.
  • Einstein 1 Service/Sales Edition: Includes Agentforce with higher conversation limits and additional AI features.
  • Developer Edition: Free; includes Agentforce for testing and development (limited conversation volume).
⚠️ Agentforce is licensed per conversation or per resolution — not per seat. Understand your license model before enabling it broadly. High-volume use cases can accumulate significant license costs.

Required Features to Enable

  • Einstein generative AI features
  • Agentforce (formerly Einstein Bots)
  • Data Cloud — required if you plan to use RAG grounding or unified profiles in agents
  • Messaging for In-App and Web — required for web/mobile deployment channels

Who Needs Access?

  • Admins: Configure agents, topics, channels, permissions, and deployment settings.
  • Developers: Build Apex actions and Flow actions; deploy via source control or Change Sets.
  • Business Analysts: Design topic instructions and test agent behavior in the Testing Center.
  • Service Operations: Monitor agent performance via the Activity Tracker.

🔌 Enabling Agentforce in Your Org

Step-by-Step Activation

  1. Navigate to Setup → Einstein → Einstein Generative AI and toggle Einstein Generative AI to On. Accept the terms of service.
  2. Navigate to Setup → Einstein → Agentforce → Settings and enable Agentforce. This activates the agent runtime in your org.
  3. Optionally enable Einstein Trust Layer settings customization (it's on by default — you only need to visit settings if you want to change PII masking sensitivity or toxicity filters).
  4. If using Data Cloud for grounding, navigate to Setup → Data Cloud → Data Cloud Settings and confirm Data Cloud is provisioned and connected to your org.

Verification

After enabling, navigate to Setup → Agentforce → Agents. If you see the Agents list page (even if empty), Agentforce is enabled. If you see a "Feature Not Enabled" message, return to the Einstein settings and confirm activation.

💡 Enabling Agentforce does not immediately activate any agents or expose any AI features to users — you still need to create and deploy agents before any user-facing changes occur.

🔒 Permissions & Profiles

Admin/Builder Permissions

Users who build and configure agents need these permissions (assignable via Permission Set):

  • Manage Bots — Create, edit, and delete agent configurations.
  • Create and Customize Bots — Configure topics, instructions, and actions.
  • View Setup and Configuration — Access Setup pages.
  • Customize Application — Needed to create and modify Flow actions and custom objects used by agents.
  • Author Apex — Required for developers writing Apex actions.

Integration User Permissions

Agentforce agents execute actions in the context of a dedicated Integration User. This user needs:

  • Read access to all objects/fields the agent needs to query
  • Create/Edit access to objects the agent will write to (e.g., Case, Task)
  • Named Credential access for any external API actions
  • No System Administrator profile — follow the principle of least privilege

Creating the Integration User

  1. Create a dedicated profile: "Agentforce Integration Profile" — clone Minimum Access User and add only required object permissions.
  2. Create a new user with type: Integration User (doesn't consume a regular user license).
  3. Assign the Integration Profile to this user.
  4. In your agent's Configuration → Integration User, select this dedicated user.

End-User Permissions

End users who chat with agents typically don't need special Salesforce permissions — they interact through the messaging widget or Experience Cloud, not directly through Salesforce. However, if the agent needs to access user-specific data, the authenticated user's profile must allow read access to their own records.

🏖️ Sandbox Strategy

Never build directly in production. A well-structured sandbox strategy is essential for reliable Agentforce development.

Recommended Sandbox Tiers

  • Developer Sandbox: Individual developers build and unit test here. Multiple sandboxes for multiple team members. Data is minimal/synthetic — no real customer data.
  • Developer Pro Sandbox: Slightly larger — for developers working on features that need more data volume to test correctly (bulk flows, performance testing).
  • Full Sandbox: Production-like data volume. Used for end-to-end agent testing, performance validation, and user acceptance testing (UAT). Refresh before major release cycles.
  • Production: The live environment. Always deploy from a sandbox, never build directly here.

What to Test in Each Tier

  • Developer Sandbox: Unit test individual actions (Flow, Apex). Test individual topic routing. Verify input/output variable mappings.
  • Full Sandbox / UAT: End-to-end agent conversations. Performance testing (response latency under realistic data volume). Business stakeholder acceptance testing. Security review.
  • Production (with monitoring): Phased rollout (10% → 50% → 100% traffic). Monitor escalation rate and CSAT closely in the first 72 hours after deployment.
💡 Agentforce agent configurations are metadata — they can be version controlled and deployed exactly like Apex classes and Flow metadata. This makes CI/CD pipelines practical.

🚀 The Deployment Process

Deploying Agentforce configuration from sandbox to production follows the same metadata deployment patterns as all Salesforce configuration.

What Gets Deployed

Agentforce deployments typically include the following metadata types:

  • BotDefinition: The agent configuration (name, description, integration user, channels)
  • BotVersion: Versioned agent configurations
  • BotBlock / BotDialog / GenAiPlugin: Topic and action metadata
  • Flow: All autolaunched flows used as agent actions
  • ApexClass: Apex action classes
  • PromptTemplate: Prompt Builder templates
  • NamedCredential: External API credentials (credentials themselves are environment-specific — only the schema is deployed, credentials are entered per-org)

Deployment Sequence

Order matters. Deploy in this sequence to avoid dependency errors:

  1. Custom objects and fields (if any new schema changes)
  2. Apex classes (action implementations)
  3. Flows (action logic)
  4. Prompt Templates
  5. Agent configuration (BotDefinition, topics, actions)
  6. Named Credential schema (not credentials)
  7. Permission Set updates

📦 Change Sets

Change Sets are Salesforce's built-in, point-and-click deployment mechanism. Good for smaller teams, less frequent deployments, or organizations that prefer a UI-driven workflow.

Creating an Outbound Change Set

  1. In your sandbox, navigate to Setup → Deployment → Outbound Change Sets → New.
  2. Give the Change Set a descriptive name: "Agentforce-OrderManagement-v2.1"
  3. Add components:
    • Add your Agent configuration components (Bot Definition)
    • Add all dependent Flows
    • Add all dependent Apex classes
    • Add Prompt Templates
    • Use Add Dependencies to automatically discover referenced components
  4. Upload the Change Set. It appears in the target org's Inbound Change Sets.

Deploying an Inbound Change Set to Production

  1. In production, navigate to Setup → Deployment → Inbound Change Sets.
  2. Find your Change Set and click Validate first — this runs the deployment checks without actually committing. Review any errors.
  3. Fix errors in the sandbox, re-upload, and re-validate until clean.
  4. Schedule the deployment for a low-traffic window.
  5. Click Deploy. Monitor the deployment status page.

Change Set Limitations

  • No version control — no git history, no diff comparison
  • Cannot roll back easily — a failed deployment may leave the org in a partial state
  • Manual dependency management — easy to miss a component
  • No automated testing integration

For larger teams or frequent releases, consider DevOps Center (below) or a Salesforce CLI-based CI/CD pipeline.

🔧 DevOps Center

Salesforce DevOps Center is a source-driven deployment tool built into Salesforce that bridges the gap between Change Sets and full CLI/CI-CD pipelines. It integrates directly with GitHub.

Key Concepts

  • Project: A DevOps Center project represents your application. It maps to a GitHub repository.
  • Pipeline: The ordered sequence of environments (Developer Sandbox → Full Sandbox → Production) that changes flow through.
  • Work Item: A deployable unit of work — equivalent to a ticket/feature branch in traditional dev. Each Work Item tracks which metadata components are associated with it.
  • Bundled Change: A group of Work Items deployed together as a release.

DevOps Center Workflow

  1. Developer creates a Work Item in DevOps Center linked to their GitHub feature branch.
  2. Developer makes changes in their Developer Sandbox (flows, Apex, agent config).
  3. Changes are tracked as metadata commits to the feature branch.
  4. Developer creates a pull request; peer review in GitHub.
  5. After merge, DevOps Center promotes the change through the pipeline (Dev Sandbox → UAT Sandbox → Production).
  6. Each stage requires a manual promotion trigger (or can be automated via GitHub Actions).

DevOps Center vs. Change Sets

FactorChange SetsDevOps Center
Version controlNoYes — GitHub integration
RollbackManual, complexGit revert + re-deploy
Peer reviewNoGitHub pull request workflow

Setup complexityLowMedium
Recommended forSmall teams, simple configsMedium/large teams, regular releases

📊 Monitoring Setup

Einstein Activity Tracker

Navigate to Setup → Agentforce → Activity Tracker to access the built-in monitoring dashboard. Configure it to track:

  • Conversations per day (volume trending)
  • Escalation rate per agent and per topic
  • Average turn count per conversation
  • Top failing topics (by escalation)
  • Action error rate per action type

Setting Up Alert Rules

Configure email alerts for critical thresholds via Setup → Workflow Rules or Flow → Scheduled Flow:

  • Alert when escalation rate exceeds 30% in a rolling 24-hour window
  • Alert when action error rate exceeds 5%
  • Alert when daily conversation volume drops by more than 50% (indicates a channel outage)

Custom Monitoring Dashboard

For richer analytics, build a CRM Analytics (Tableau CRM) dashboard on top of the BotSession and related objects that Agentforce writes to. Useful metrics to surface:

  • Containment rate by time of day / day of week
  • Escalation rate by customer tier (do high-value customers escalate more?)
  • Average resolution time (turns to resolution)
  • Topic distribution — which topics are most used?

🔑 Named Credentials Configuration

Named Credentials securely store authentication details for external APIs. They prevent API keys and passwords from being hardcoded in Apex or Flow and enable org-specific credentials to be managed without code changes.

Creating a Named Credential

  1. Navigate to Setup → Security → Named Credentials → New.
  2. Choose the credential type: Named Credential (for external endpoints) or External Credential (for OAuth flows).
  3. Enter the Label and Name (used in code: callout:MyAPI/endpoint).
  4. Enter the URL — the base URL of the external service.
  5. Configure authentication: API key (custom header), Basic Auth (username/password), OAuth 2.0, JWT Bearer, or no authentication.
  6. Enable Allow Merge Fields in HTTP Body if your Apex actions need to pass Salesforce data in request payloads.

Environment-Specific Credentials

Named Credentials are org-specific — the credential definition is deployed via Change Set or DevOps Center, but the actual credentials (API keys, passwords) are entered manually in each org. This ensures production credentials are never stored in source control or passed through sandboxes.

🏛️ Enterprise Governance Framework

AI Governance Structure

For organizations with multiple Agentforce deployments, establish formal governance:

  • AI Center of Excellence (CoE): Central team responsible for Agentforce platform standards, shared component libraries, and cross-org best practices. Owns the master Action library and approved Topic templates.
  • Line of Business AI Owners: Business units that own their specific agent configurations. Accountable for agent performance, escalation rates, and continuous improvement.
  • Risk & Compliance Review: Mandatory review gate for any agent that processes regulated data (healthcare, financial, legal).

Change Approval Process

Define the approval required for different change types:

Change TypeReview RequiredApproval Process
New Topic instruction wording (minor)Business ownerAsync Slack approval
New Topic (scope expansion)Business owner + SecurityFormal change ticket
New external API integrationSecurity + ArchitectureArchitecture review board
New agent accessing regulated dataRisk + Compliance + LegalFull compliance review
LLM provider changeRisk + Legal + AI CoEBoard-level approval

Documentation Requirements

Maintain living documentation for each deployed agent:

  • Agent purpose and business objectives
  • Data categories accessed (list every Salesforce object and field)
  • External systems integrated (with data flow diagram)
  • Compliance risk assessment
  • Test results from UAT (with test case coverage)
  • Monitoring thresholds and alert configuration
  • Runbook for common incidents (high escalation rate, action failures)

⚙️ Full CI/CD Pipeline

For mature engineering teams, a fully automated CI/CD pipeline enables rapid, reliable deployments with comprehensive testing at every stage.

Recommended Stack

  • Source Control: GitHub (or GitLab/Bitbucket)
  • CI/CD Platform: GitHub Actions, Copado, Gearset, or Flosum
  • Testing: Salesforce CLI (sf apex run test), Flow Testing API, custom agent conversation tests
  • Package Management: Salesforce DX Unlocked Packages (for modular deployment)

Pipeline Stages

  1. PR Validation (on pull request):
    • Deploy to a fresh scratch org
    • Run all Apex test classes (sf apex run test --target-org scratch --test-level RunLocalTests)
    • Run Flow test cases via the Flow Testing API
    • Validate agent metadata deploys without errors
    • Block merge if any test fails or code coverage < 75%
  2. Merge to develop → Full Sandbox deploy
    • Deploy to Full Sandbox automatically
    • Run regression suite of agent conversation tests (scripted via Agent API)
    • Post results to Slack/Teams channel
  3. Release branch → Production deploy
    • Manual gate: requires release manager approval in GitHub
    • Deploy during scheduled maintenance window
    • Run smoke tests via Agent API immediately post-deploy
    • Monitor escalation rate for 30 minutes post-deploy; automated rollback trigger if rate exceeds threshold

Salesforce CLI Key Commands

# Deploy metadata to org
sf project deploy start --target-org production --manifest package.xml

# Validate without deploying (pre-deployment check)
sf project deploy start --dry-run --target-org production --manifest package.xml

# Run Apex tests
sf apex run test --target-org production --test-level RunLocalTests --result-format tap

# Create a scratch org for CI
sf org create scratch --definition-file config/project-scratch-def.json --set-default

# Retrieve metadata from an org (source tracking)
sf project retrieve start --target-org my-sandbox

📈 Scaling Considerations

Conversation Volume Scaling

  • Agentforce scales automatically — Salesforce manages the underlying infrastructure. However, your connected systems (external APIs, backend services) may not. Load test your external API integrations at expected peak agent conversation volume before launch.
  • Monitor the Agentforce rate limit consumption dashboard — high-volume orgs may need to request limit increases from Salesforce.
  • For planned peak events (product launches, seasonal campaigns), notify your Salesforce account team in advance for capacity planning.

Multi-Org Architecture

Very large enterprises may deploy Agentforce across multiple Salesforce orgs (e.g., separate orgs for different regions, subsidiaries, or business units). Key considerations:

  • Each org has independent license allocation — plan license budgets per org.
  • Shared action libraries can be packaged as Unlocked Packages and deployed across orgs.
  • Consider a Hub org with Salesforce Connect for cross-org data access, rather than duplicating data.
  • Centralize Einstein Trust Layer audit logs from all orgs in a single compliance data store (Data Cloud or external SIEM).

Data Cloud at Scale

  • For orgs with 50M+ unified profiles, schedule identity resolution runs during off-peak hours — resource-intensive at high volume.
  • Use Data Cloud's data tier settings to categorize hot (frequently accessed) vs. cold (archival) data — this optimizes both cost and query performance.
  • Monitor Data Cloud job queues in the Jobs dashboard — long queue times indicate resource contention and may require capacity adjustments.

🏆 Salesforce AI Certification Paths

Certification Recommendations by Role

AI Associate

For: Anyone starting with Salesforce AI. Covers: AI concepts, Einstein features, Agentforce overview, ethical AI. No technical prerequisites.

Study path: Trailhead AI Associate Trailmix (8–10 hours)

AI Specialist

For: Developers and admins implementing Agentforce. Covers: Agent configuration, Prompt Builder, Einstein features, Trust Layer. Recommends AI Associate first.

Study path: AI Specialist Trailmix (20–30 hours)

Data Cloud Consultant

For: Architects and consultants deploying Data Cloud. Covers: Data ingestion, identity resolution, segmentation, RAG architecture, governance.

Study path: Data Cloud Consultant Trailmix

Platform Developer I & II

For: Developers writing Apex actions and Flows. Covers: Core Apex, SOQL, LWC, deployment. Foundational for Agentforce development.

Study path: Platform Dev Trailmixes

Recommended Study Sequence

  1. AI Associate (foundation for everyone)
  2. Salesforce Administrator (if not already certified)
  3. AI Specialist (for Agentforce practitioners)
  4. Platform Developer I (for those writing Apex actions)
  5. Data Cloud Consultant (for those implementing RAG and CDP)

Maintaining Certifications

Salesforce releases maintenance modules twice a year (Spring and Summer releases). Certified individuals must complete maintenance exams annually to keep their certifications active. AI-related certifications tend to have substantial maintenance content given the pace of platform evolution. Subscribe to the Trailblazer Community release notes to stay ahead of changes.
