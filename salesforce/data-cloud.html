☁️ What is Salesforce Data Cloud?

Salesforce Data Cloud is a real-time Customer Data Platform (CDP) built natively into Salesforce. It is the central data layer for the entire Salesforce AI platform — providing the data foundation that powers Agentforce, Einstein, Marketing Cloud personalization, and analytics.

The core problem Data Cloud solves: enterprise customer data is scattered. A customer might exist as a contact in Salesforce CRM, a subscriber in Marketing Cloud, a shopper in Commerce Cloud, a visitor in web analytics, and a ticket submitter in your support portal. These are four or five disconnected records for the same person. Data Cloud ingests all of these, resolves them into a single unified profile, and makes that profile available in real time across every Salesforce product.

Why it matters for AI

  • Better agent responses: An Agentforce agent with access to a unified profile can personalize its response based on the customer's full relationship with your company — not just the last support ticket.
  • Grounded AI: Data Cloud powers vector search, enabling agents to retrieve relevant knowledge content and answer questions without hallucinating.
  • Real-time personalization: Marketing Cloud and Journey Builder can react to customer data changes as they happen — not hours later via batch sync.
  • Unified analytics: Tableau and CRM Analytics can query a single source of truth for customer metrics across all channels.
💡 Mental model: Think of Data Cloud as the "unified truth layer" that sits beneath all of Salesforce. Every app that needs to know something about a customer asks Data Cloud — not each other.

🗂️ Core Concepts

Data Lake Objects (DLOs)

A Data Lake Object is the raw landing zone for ingested data. When you connect a data source to Data Cloud, the raw data lands in a DLO. Think of DLOs as the "raw storage layer" — unprocessed, schema-flexible containers for incoming data streams.

Data Model Objects (DMOs)

Data Model Objects are the structured, mapped objects that represent business entities in Data Cloud's standard data model. Common DMOs include: Individual (person), Contact Point Email, Contact Point Phone, Sales Order, Case, Engagement (web click/email open), etc. When you map your DLO fields to DMO fields, you're normalizing raw data into a common schema that allows identity resolution and profile building.

Identity Resolution

The process of linking records from different sources that belong to the same real person. For example, matching a Marketing Cloud subscriber record (identified by email) with a Salesforce CRM contact (identified by phone number) to confirm they're the same individual. Identity resolution runs as a continuous background process and is the foundation of the unified profile.

Unified Profiles

The output of identity resolution. Each unified profile represents a single individual, aggregated from all matched source records. The profile includes all contact points, engagement history, purchase history, support history, and any calculated metrics — a 360-degree view of the customer.

Segments

A filtered subset of unified profiles that share common characteristics. Example: "High-value customers who haven't purchased in 90 days and have an open support case." Segments can be activated to Marketing Cloud for targeted campaigns, or used by Agentforce agents to personalize responses based on segment membership.

Data Spaces

Data Cloud supports multiple Data Spaces within a single org — essentially isolated data environments for different business units or geographies. Data in one Data Space is not visible to another unless explicitly shared. This enables compliance isolation for multi-national organizations.

🔌 Data Connectors Overview

Data Cloud connects to dozens of data sources via pre-built connectors. Here are the most common categories:

Salesforce Connectors (Native)

  • CRM Connector: Syncs standard and custom Salesforce objects (Contacts, Accounts, Cases, Opportunities, custom objects) in near real time.
  • Marketing Cloud Connector: Brings in subscriber data, email engagement (opens, clicks), journey events, and audience lists.
  • Commerce Cloud Connector: Syncs order data, cart events, product interactions, and customer purchase history.
  • Service Cloud Voice Connector: Imports call transcripts and interaction data from voice channel.

Cloud Storage Connectors

  • Amazon S3 — batch file uploads (CSV, JSON, Parquet)
  • Google Cloud Storage
  • Azure Blob Storage

Direct Data Ingestion API

For custom integrations, use the Ingestion API to push records directly into Data Cloud from any HTTP-capable system. Ideal for: mobile app events, IoT devices, custom web tracking, or systems without a pre-built connector.

MuleSoft Anypoint

Enterprise integration via MuleSoft. Connect virtually any system (SAP, Workday, legacy databases, custom APIs) to Data Cloud via pre-built Anypoint connectors or custom integration flows.

👤 Unified Customer Profiles — Walkthrough

Here's how a unified profile is built end-to-end for a real customer scenario.

Scenario: Emma, a customer

Emma has interacted with your company across multiple channels:

  • CRM: Contact record — Name: Emma Wilson, Email: emma@work.com, Phone: 555-0101
  • Marketing Cloud: Subscriber — emma.w@personal.com, subscribed to newsletter
  • E-Commerce: Account — emma.wilson@gmail.com, 3 orders in 12 months
  • Support: Case submitted via web form — emma@work.com

Step 1 — Ingestion

Each source's data flows into its own DLO in Data Cloud. Emma now exists as four separate records across four DLOs.

Step 2 — Mapping to DMOs

Each DLO's fields are mapped to the standard Data Cloud DMO schema: Email addresses become Contact Point Email records. Phone numbers become Contact Point Phone records. Orders become Sales Order records.

Step 3 — Identity Resolution

Identity resolution runs its configured ruleset. It matches emma@work.com (CRM) to emma@work.com (support), then finds the phone number match to link the commerce account. After resolution, all four records are linked under a single Individual ID.

Step 4 — Unified Profile

Emma's unified profile now shows: 3 email addresses, 1 phone number, 3 e-commerce orders, 1 open support case, newsletter subscriber, CRM contact. Any Salesforce product can query this profile by any of Emma's identifiers.

💡 Profile completeness directly impacts agent response quality. An agent that can see Emma's full order history can answer "have I ordered this before?" — an agent with only the support ticket cannot.

Connector Configuration Walkthrough

For the Salesforce CRM Connector (most common):

  1. Navigate to Data Cloud Setup → Data Stream → New.
  2. Select Salesforce CRM as the source.
  3. Choose the object to sync (e.g., Contact, Case, Opportunity).
  4. Select fields to include — only include fields you will actively use. Unused fields increase data processing costs.
  5. Set the refresh schedule: Real-time (triggers on record change via Platform Events) or Scheduled (batch refresh at set intervals).
  6. Map the DLO fields to DMO fields on the next screen.

Field Mapping Best Practices

  • Map primary identifiers (email, phone, contact ID) to the standard DMO Contact Point fields — identity resolution depends on this.
  • Use the Data Stream Category field to correctly classify your data stream type (Profile, Engagement, Other). This affects how identity resolution treats the records.
  • Mark fields as Match Key if they should be used in identity resolution matching rules (e.g., email, phone, CRM ID).
  • Map date fields to the standard DateTime type — inconsistent date formats are the most common cause of ingestion failures.

🔍 Identity Resolution

Identity resolution is the process that transforms disconnected records from multiple sources into unified individual profiles. It runs as a continuous background job and is the most architecturally important configuration in Data Cloud.

Matching Rules

Matching rules define the criteria used to decide that two records belong to the same individual. Data Cloud supports two types:

  • Deterministic matching: Exact-match rules based on specific field values. Example: "If two records have the same email address AND the same phone number, they match." High precision, no false positives, but requires exact data consistency across sources.
  • Probabilistic (fuzzy) matching: Likelihood-based rules that match even when values aren't identical. Example: "If two records have very similar names AND the same zip code AND one has an email that appears in the other's domain, they probably match." Higher recall but can produce false positives.

Rule Priority and Reconciliation

When records are matched, the resulting unified profile must decide which source value to use for each attribute (e.g., if CRM and Marketing Cloud have different phone numbers for the same person, which is the "true" phone number). This is controlled by Reconciliation Rules:

  • Most Frequent: Use the value that appears most often across matched records.
  • Most Recent: Use the value from the most recently updated record.
  • Source Priority: Explicitly define which data source takes precedence (e.g., CRM > Marketing Cloud > Commerce).

Monitoring Identity Resolution Quality

  • Monitor the Match Rate — what % of incoming records matched to an existing profile vs. created a new one.
  • Audit the Merge Rate — how many separate profiles were merged into one during the last run.
  • Spot-check unified profiles in the Data Cloud Profile Explorer to verify that merged records genuinely represent the same individual.
  • A low match rate often indicates that match key fields (email, phone) are not consistently populated across source systems.

📊 Calculated Insights

Calculated Insights are derived metrics computed from unified profile data and stored back on the profile. They transform raw event data into actionable business metrics available in real time.

Examples

  • Lifetime Value (LTV): Sum of all order amounts for a customer, segmented by calendar year.
  • Days Since Last Purchase: Recency metric used for lapsed customer targeting.
  • Purchase Frequency: Average number of orders per month over the last 12 months.
  • Support Intensity: Number of cases opened in the last 90 days — a risk indicator for churn.
  • Email Engagement Score: Weighted score of opens, clicks, and conversions over the last 30 days.

Creating a Calculated Insight

Navigate to Data Cloud → Calculated Insights → New. You write the insight using ANSI SQL against your Data Cloud DMOs. Example:

SELECT
    ssot__Individual__c AS individual_id,
    SUM(ssot__TotalAmount__c) AS lifetime_value,
    COUNT(ssot__Id__c) AS total_orders,
    MAX(ssot__OrderedDate__c) AS last_order_date
FROM ssot__SalesOrder__dlm
GROUP BY ssot__Individual__c

Using Insights in Agents

Once calculated, insights are stored on the unified profile and available to Agentforce agents as profile attributes. An agent that knows a customer's LTV and support intensity can tailor its tone and escalation behavior without any explicit rule configuration — the LLM infers the appropriate response from the context.

🎯 Segmentation & Activation

Building Segments

Segments are built in the Data Cloud Segment Builder — a visual drag-and-drop interface that filters unified profiles based on profile attributes, Calculated Insights, and engagement history.

Example segment: "High-value lapsed customers at risk" =

  • Lifetime Value > $5,000 (from Calculated Insight)
  • Last Order Date > 90 days ago
  • No open support cases
  • Email engagement score > 50 in the last 90 days (still reading our emails)

Segment Refresh Rates

  • Real-time segments: Update within seconds as profile data changes. Only available for specific segment conditions. Highest cost.
  • Rapid segments: Refresh every 12 hours. Good for daily campaign targeting.
  • Scheduled segments: Refresh on a defined schedule (daily, weekly). For non-time-sensitive use cases.

Activation

Segments are activated — pushed to downstream systems for action. Common activation targets:

  • Marketing Cloud: Activate segment as a subscriber list for email/SMS campaigns.
  • Advertising: Push segment to Google Ads or Meta for matched audience targeting.
  • Agentforce: Use segment membership as a context variable in agent topics — e.g., "If the customer is in the 'At Risk' segment, prioritize retention over upsell."
  • Service Cloud: Flag high-value segment members for priority routing in the contact center.

🤖 Data Cloud for Agentforce

Data Cloud is the data backbone for Agentforce. This section covers the two main integration points: profile grounding and knowledge retrieval (RAG).

Profile Grounding

When an authenticated user starts an Agentforce session, their Data Cloud unified profile is automatically available as session context. The Atlas Reasoning Engine can reference profile attributes in its planning without requiring explicit action invocations for common data lookups.

To configure profile grounding: in your Agent configuration, enable Data Cloud Customer Profile under Agent Context. Specify which profile attributes to include in the agent context window (be selective — including too many attributes increases token consumption and latency).

Knowledge Retrieval (RAG)

For agents that need to answer questions based on your organization's specific knowledge content — policies, FAQs, product documentation — configure Data Cloud's Vector Search as a retrieval source:

  1. Create a Data Cloud Vector Database object for your knowledge content type.
  2. Connect your content source (Knowledge Articles, uploaded PDFs, web crawl, etc.).
  3. Data Cloud automatically chunks the content and generates vector embeddings.
  4. In Prompt Builder, add a Data Cloud Search resource to your prompt template — this executes a semantic search at inference time and injects the most relevant chunks as grounding context.

🔒 Data Governance & Privacy

Consent Management

Data Cloud has a built-in Consent Manager that tracks customer consent preferences across channels. Consent decisions (opt-in/opt-out) are enforced automatically when activating segments — profiles without the required consent for a given activation channel are automatically excluded.

Data Retention Policies

Configure data retention rules per Data Lake Object. Records older than the retention window are automatically purged. This directly supports GDPR's "right to be forgotten" — when a deletion request is processed, it propagates across all DLOs and the unified profile is updated.

Right to Be Forgotten Workflow

  1. Receive a data subject deletion request.
  2. Trigger a Deletion Request via the Data Cloud API or the Privacy Center interface.
  3. Data Cloud identifies all records linked to the individual's unified profile across all DLOs.
  4. Records are deleted from all DLOs within the configured SLA (typically 30 days for GDPR).
  5. The unified profile is deleted. An audit record is maintained to prove deletion occurred (without retaining the deleted data itself).

Data Spaces for Compliance Isolation

Use separate Data Spaces for different regulatory jurisdictions (e.g., EU customers in a dedicated Data Space with stricter retention policies). Data Spaces prevent cross-contamination of data subject to different regulatory frameworks.

🔢 Vector Search & Embeddings

Vector search is the foundation of RAG (Retrieval-Augmented Generation) in Data Cloud. Understanding how it works at the technical level is essential for building high-quality knowledge retrieval systems.

How Embeddings Work

An embedding is a numerical representation of text as a high-dimensional vector (typically 768–3072 dimensions). Similar meanings produce similar vectors — measured by cosine similarity or dot product. The embedding process:

  1. Text content (knowledge article, FAQ, policy document) is chunked into segments of a configured size (typically 500–1000 tokens per chunk, with overlap).
  2. Each chunk is passed through an embedding model (Data Cloud uses a hosted embedding model — you don't manage it directly).
  3. The resulting vector is stored in the Vector Database object alongside the original text chunk and source metadata.

Semantic Search at Inference Time

When an Agentforce agent needs to retrieve knowledge:

  1. The agent's current query (or a derived search query) is passed to the embedding model to generate a query vector.
  2. The query vector is compared against all stored content vectors using approximate nearest neighbor (ANN) search.
  3. The top K most similar chunks are returned (K is configurable — typically 3–10).
  4. These chunks are injected into the prompt as grounding context.

Chunking Strategy Matters

  • Too small chunks: Each chunk lacks sufficient context for the LLM to understand it. The retrieved chunk might be a sentence fragment that's technically similar but lacks the surrounding explanation.
  • Too large chunks: Less precise retrieval — a 2000-token chunk matches many queries broadly, reducing relevance of retrieved content.
  • Recommended approach: 400–600 tokens per chunk with 10–15% overlap. Structure chunks around natural document boundaries (paragraphs, sections) rather than arbitrary token counts.
  • Hybrid chunking: For structured documents (FAQs, policy tables), consider chunking by question-answer pair rather than fixed token size.

Metadata Filtering

Vector search can be combined with metadata filters to scope retrieval. Example: retrieve only from knowledge articles tagged "returns_policy" when the agent is handling a returns topic. Metadata filtering dramatically improves retrieval precision in large knowledge bases.

🏗️ Building RAG Pipelines

End-to-End RAG Architecture

A production RAG pipeline has three stages:

Stage 1: Indexing Pipeline (runs continuously)

  1. Source content (Salesforce Knowledge Articles, uploaded PDFs, web-crawled pages) is ingested into a Data Cloud Data Lake Object.
  2. A data stream maps the DLO to the Vector Database DMO.
  3. Data Cloud's embedding job processes new/updated chunks automatically — no manual re-indexing required.
  4. Deleted source content automatically removes the corresponding vectors via the data stream's delete propagation.

Stage 2: Retrieval at Inference Time

In Prompt Builder, add a Data Cloud Search resource to your prompt template:

  • Configure the search query: usually the user's message or a derived search query from the conversation context.
  • Set K (number of results): typically 3–5 for conversational agents (more dilutes relevance).
  • Apply metadata filters where applicable.
  • Configure the output: how retrieved chunks are formatted and injected into the prompt.

Stage 3: Generation with Grounding

The prompt template injects retrieved chunks into a structured prompt:

You are a customer service agent for Acme Corp.
Answer the customer's question using ONLY the information
provided in the context below. If the answer is not in the
context, say "I don't have that information" — do NOT make up answers.

CONTEXT:
{!DataCloudSearch.results}

CUSTOMER QUESTION:
{!$Input.userMessage}

Evaluating RAG Quality

  • Retrieval precision: Are the retrieved chunks actually relevant to the query? Score manually on a test set of 50–100 queries.
  • Answer faithfulness: Does the LLM's answer stay within the retrieved context (not hallucinate)? Use an LLM-as-judge evaluation pattern.
  • Coverage: What % of real user queries can be answered from the knowledge base? Identify gaps and add content to fill them.
  • Latency: The vector search adds ~200–500ms of latency. Monitor retrieval time separately from LLM generation time.

⚡ Streaming Data Ingestion

Salesforce Event Bus Integration

Data Cloud can subscribe to Salesforce Platform Events and Change Data Capture (CDC) streams for near-real-time data ingestion from Salesforce orgs. This enables sub-second profile updates when CRM records change.

Configure via: Data Cloud → Data Streams → New → Salesforce CRM → Real-Time. Enabling "Real-Time" mode activates CDC-based streaming for the selected object.

Streaming Ingestion API

For non-Salesforce event sources, use the Streaming Ingestion API to push events directly into Data Cloud:

POST https://[instance].salesforce.com/api/v1/ingest/sources/[sourceId]/[objectName]
Authorization: Bearer {access_token}
Content-Type: application/json

{
  "data": [
    {
      "CustomerId__c": "CUST-001",
      "EventType__c": "PageView",
      "PageUrl__c": "/products/widget-pro",
      "Timestamp__c": "2025-09-15T14:23:00Z",
      "SessionId__c": "sess-xyz-123"
    }
  ]
}

Web SDK (First-Party Event Collection)

Salesforce's Personalization Web SDK enables first-party event collection directly from your website into Data Cloud — without third-party cookies. It tracks page views, clicks, form submissions, and custom events with full consent management integration. Implement by adding the SDK script to your site and configuring event mappings to your Data Cloud DLO schema.

🔌 Data Cloud APIs

Query API

Execute ANSI SQL queries against Data Cloud DMOs via REST:

POST /services/data/v62.0/ssot/query
Authorization: Bearer {token}
Content-Type: application/json

{
  "sql": "SELECT ssot__Name__c, ssot__Email__c FROM ssot__Individual__dlm WHERE ssot__IndividualId__c = 'IND-001' LIMIT 1"
}

Profile API

Retrieve a specific unified profile by identifier:

GET /services/data/v62.0/ssot/profile/individuals/{individualId}
Authorization: Bearer {token}

Deletion API (Right to be Forgotten)

POST /services/data/v62.0/ssot/deletion-jobs
Authorization: Bearer {token}
Content-Type: application/json

{
  "deleteRequests": [
    {
      "subjectType": "Individual",
      "subjectId": "IND-001",
      "reason": "GDPR Right to Erasure"
    }
  ]
}

🗄️ Custom Data Models

Data Cloud's standard data model (based on the Salesforce CDP Data Model) covers most common entities. For industry-specific or company-specific requirements, you can extend it with custom DMOs.

When to Create Custom DMOs

  • Your business data doesn't map cleanly to any standard DMO (e.g., a healthcare encounter record, a financial portfolio, a manufacturing work order).
  • You need to track relationships between entities that aren't in the standard model.
  • You have high-volume proprietary data (IoT sensor readings, financial tick data) that needs first-class treatment in the model.

Custom DMO Design Principles

  • Always include an Individual ID foreign key on any custom DMO that should be linked to a unified profile — this is what connects your data to identity resolution.
  • Use standard field types (text, number, date, boolean) — avoid overly complex nested structures that make querying difficult.
  • Follow the naming convention: custom DMOs typically end in __dlm.
  • Document your custom DMO schema thoroughly — Data Cloud schemas are long-lived and hard to change once data is flowing.

🚀 Performance at Scale

Identity Resolution Performance

  • Identity resolution is resource-intensive at scale. For orgs with 50M+ profiles, schedule full reconciliation runs during off-peak hours.
  • Prioritize deterministic matching rules — they are significantly faster than probabilistic rules.
  • Limit the number of active match rules to the minimum needed. Each additional rule multiplies the comparison workload.

Query Optimization

  • Use indexed fields in WHERE clauses (Individual ID, Contact Point fields, data stream source IDs are indexed by default).
  • Avoid SELECT * — explicitly list the fields you need. Wide-schema queries are significantly slower.
  • For Calculated Insights with complex aggregations, materialize intermediate results as helper insights rather than computing everything in one query.

Segment Performance

  • Real-time segments are expensive. Reserve them for truly time-critical use cases (<5% of your segments).
  • Reuse segment building blocks — if multiple segments share a common filter (e.g., "active customers only"), create a base segment and build derived segments on top of it.
  • Monitor segment build times in the Data Cloud Jobs dashboard. Segments that take >30 minutes typically indicate a query optimization opportunity.
