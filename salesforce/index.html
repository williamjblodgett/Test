🔍 Platform Overview

Agentforce is Salesforce's autonomous AI agent platform built on three architectural pillars: the Atlas Reasoning Engine (the LLM-based decision layer), Data Cloud (the real-time data retrieval and grounding layer), and the Einstein Trust Layer (the security and compliance enforcement layer).

Unlike prompt-based AI assistants, Agentforce agents operate in a continuous plan → act → observe → iterate loop. They are assigned a role (e.g., Service Agent), a set of scoped Topics, and a library of callable Actions — then they autonomously determine which actions to invoke based on the user's intent.

💡 Architectural distinction: Agentforce agents are stateful within a session. They maintain conversation context, track which actions have already been taken, and can branch logic based on intermediate results — unlike a single-turn LLM call.

Core Components

  • Agent: The top-level entity — a configured AI persona with a name, role description, and channel assignments.
  • Atlas Reasoning Engine: Orchestrates the reasoning loop using a hosted LLM (currently based on GPT-4 class models via Salesforce's infrastructure). It decides which Topic to invoke and which Actions to execute.
  • Topics: Scoped business domains (e.g., "Order Management") that define what the agent is allowed to help with, with their own instructions and action sets.
  • Actions: Callable units of work — Flows, Apex methods, Prompt Templates, or REST API calls.
  • Einstein Trust Layer: Security middleware between the agent and external LLMs — masks PII, enforces zero data retention, and logs all AI interactions.

🔄 Agent Lifecycle & Reasoning Loop

Understanding how an Agentforce agent processes a request is essential for debugging unexpected behavior and optimizing performance.

Step-by-Step Execution Flow

  1. Input received: A user message arrives via a configured channel (Messaging for In-App, Experience Cloud, API endpoint, etc.).
  2. Topic classification: The Atlas Reasoning Engine evaluates the input against all configured Topics for this agent. It selects the best-matching Topic based on Topic instructions and trigger examples.
  3. Planning phase: Within the matched Topic, the engine generates a reasoning plan — it considers the conversation history, the Topic's instructions, and the available Actions.
  4. Action invocation: The engine calls one or more Actions sequentially or in branches. Each Action returns a result (record data, confirmation, generated text, etc.).
  5. Observation & iteration: The engine evaluates action results. If the task isn't complete, it replans and calls additional Actions. This loop continues until the agent determines it has a final response.
  6. Response generation: A final natural language response is generated (optionally using a Prompt Template Action) and delivered to the user.
  7. Session state update: Conversation context is persisted for the session duration, allowing follow-up questions to reference earlier turns.
⚠️ Loop guard: Agentforce has built-in iteration limits to prevent runaway reasoning loops. If the agent cannot resolve a task within the limit, it hands off to a human or returns a fallback message. Configure this in the Agent's escalation settings.

Concrete Example: Order Status Lookup

A customer messages: "Where is my order #12345? It was supposed to arrive yesterday."

  1. Atlas matches this to the "Order Management" Topic.
  2. The engine identifies it needs to retrieve order data — invokes a Flow Action that queries the Order object via SOQL, filtered by order number.
  3. The Flow returns: Order status = "In Transit", carrier = "FedEx", estimated delivery = tomorrow.
  4. The engine detects a delay (delivery missed SLA) and invokes a second Action — a Prompt Template Action to draft an empathetic response with the tracking link.
  5. Final response is delivered. The session logs the interaction for supervisor review.

📋 Topics & Instructions

Topics are the primary scoping mechanism in Agentforce. They define what the agent knows how to do and prevent scope creep — an agent will only attempt tasks covered by its assigned Topics.

Anatomy of a Topic

  • Name: A business-meaningful label (e.g., "Case Resolution", "Lead Qualification").
  • Description: A plain-language description used by the reasoning engine to determine when this Topic is applicable. Be precise — vague descriptions lead to misrouting.
  • Instructions: Natural language behavioral guidelines for the agent within this Topic scope. Examples: "Always verify the customer's account before making changes", "Never quote pricing — escalate to Sales".
  • Actions: The specific Actions available to the agent when handling this Topic. Actions not listed here are inaccessible, even if defined elsewhere.
  • Scope boundary: If a user's request falls outside the Topic's scope, the agent either routes to another Topic or escalates to a human.

Writing Effective Instructions

Instructions are evaluated by the LLM at runtime — treat them like system prompts for a specific domain:

  • Use imperative language: "Confirm the customer's identity before accessing account details."
  • Define escalation triggers: "If the customer mentions a legal dispute, immediately escalate to a live agent."
  • Set output constraints: "Responses should be no more than 3 sentences. Always end with a follow-up question."
  • Avoid contradictory instructions — the LLM will attempt to reconcile them, often unpredictably.
💡 Instructions are not hardcoded decision trees — they are LLM-interpreted guidance. Test edge cases thoroughly in the Agent Testing Center before deploying to production.

⚡ Actions Deep Dive

Actions are the callable operations Agentforce agents invoke during reasoning. Each Action type has different use cases, invocation patterns, and limitations.

Flow Actions

Invoke an auto-launched Salesforce Flow. This is the most common Action type for reading and writing Salesforce records.

  • The Flow must be of type "Autolaunched Flow (No Trigger)" — screen flows are not supported.
  • Input variables are passed from the agent's conversation context. Output variables are returned to the reasoning engine.
  • Flow Actions have access to the full Salesforce platform: SOQL, DML, external callouts, Platform Events.
  • Performance consideration: Complex Flows with multiple SOQL queries add latency to the reasoning loop. Keep agent-facing Flows focused and fast.

Apex Actions

Invoke a public static Apex method decorated with @InvocableMethod. Use for complex logic that isn't practical in Flow.

  • Apex Actions run in the context of the running user's permissions unless with sharing is overridden.
  • Use for: complex data transformations, external callouts requiring custom HTTP handling, business rules that require procedural logic.
  • Apex governor limits apply — be mindful of SOQL row limits and CPU time in agent contexts where multiple Actions may run per turn.

Prompt Template Actions

Generate dynamic text using a Prompt Template — a structured prompt that merges Salesforce record data with LLM-generated content.

  • Templates are created in Prompt Builder and can reference Salesforce record fields using merge fields.
  • Use for: drafting emails, generating case summaries, creating personalized messages from CRM data.
  • Supports grounding with Data Cloud vector search for RAG (Retrieval-Augmented Generation) patterns.
  • All Prompt Template calls pass through the Einstein Trust Layer — PII masking is applied before reaching the LLM.

API Actions (External APIs)

Call external REST APIs directly from the agent, using Named Credentials for authentication management.

  • Define the API spec (OpenAPI/Swagger format preferred) to expose specific endpoints as callable Actions.
  • Authentication is handled via Named Credentials — secrets are never exposed in the agent configuration.
  • Use for: checking inventory in an ERP, submitting a support ticket to ServiceNow, querying a third-party logistics API.

Action Input/Output Mapping

The Atlas Reasoning Engine maps conversation context to Action inputs using its understanding of the prompt — but you can make this explicit by providing well-named input parameters and clear Action descriptions. The better your Action descriptions, the more reliably the engine invokes the right Action with the right inputs.

🛡️ Einstein Trust Layer — Internals

The Einstein Trust Layer (ETL) is Salesforce's security middleware that sits between your Agentforce agents and any external LLM provider. It enforces data privacy and compliance policies in real time without requiring custom code.

How It Works

  1. Data assembly: The agent assembles a prompt, which may include Salesforce record data, user inputs, and conversation history.
  2. PII detection & masking: The ETL scans the prompt for personally identifiable information (email addresses, phone numbers, SSNs, account numbers) using pattern matching and ML-based detection. Detected PII is replaced with anonymized tokens (e.g., [EMAIL_1]).
  3. Prompt sent to LLM: The masked prompt is forwarded to the configured LLM provider (OpenAI, Anthropic, or Salesforce's hosted model).
  4. Response received: The LLM response is returned. The ETL re-inserts the original PII in place of the tokens where appropriate in the final response.
  5. Toxicity filtering: The response is scanned for harmful content before being delivered to the end user. Blocked responses trigger a configurable fallback message.
  6. Audit logging: Every prompt/response pair is logged in the Einstein AI Audit Trail, accessible via Salesforce Data Cloud or direct query. Logs include: timestamp, user, masked prompt, response, and any filters triggered.

Zero Data Retention

Salesforce negotiates zero data retention agreements with its LLM providers. This means the external LLM does not store your prompts, cannot use your data for model training, and your data is not accessible to other tenants. This is contractually enforced and is a key differentiator from consumer LLM APIs.

Key ETL Capabilities

  • Dynamic grounding: Injects verified Salesforce record data into prompts at inference time — reducing hallucination risk for domain-specific responses.
  • Data masking customization: Admins can define custom masking rules for organization-specific sensitive fields beyond standard PII patterns.
  • Model gateway: Acts as an abstraction layer — you can switch LLM providers without changing agent configuration.
  • Rate limiting & monitoring: Tracks LLM token consumption per org, per agent, and per user for cost management.

☁️ Data Cloud Integration

Salesforce Data Cloud is a real-time customer data platform (CDP) that acts as the data backbone for Agentforce. It enables agents to access unified customer profiles and perform semantic (vector) search across unstructured knowledge content.

Unified Customer Profiles

Data Cloud ingests data from multiple sources — Salesforce CRM, Marketing Cloud, Commerce Cloud, external ERPs, web/mobile event streams — and resolves them into a single unified profile per customer.

  • Agents can query these profiles in real time using Data Cloud's Retrieval Augmented Generation (RAG) capabilities.
  • Profile data is surfaced in agent context without requiring explicit SOQL queries — the reasoning engine can reference "the customer's recent purchases" and Data Cloud resolves the lookup.
  • Profile completeness directly impacts agent response quality — incomplete data = less contextually accurate responses.

Vector Search & RAG

For knowledge base retrieval, Agentforce uses Data Cloud's vector search to find semantically relevant content:

  • Knowledge articles, case history, product documentation, and policy documents are chunked and embedded as vectors in Data Cloud.
  • When an agent needs reference content, it submits a semantic query — the embedding similarity search returns the most contextually relevant chunks.
  • These chunks are inserted into the prompt as grounding context, dramatically reducing hallucinations on organization-specific questions.
  • Embedding is handled automatically when content is connected to Data Cloud — no custom ML pipeline required.

Real-Time Data Considerations

  • Data Cloud ingestion latency varies by source connector — batch-synced sources may lag by minutes to hours, while real-time event sources (e.g., web clicks via the Web SDK) are near-instantaneous.
  • Agent responses are only as current as the data in Data Cloud. For truly real-time CRM data (e.g., just-submitted orders), use Flow Actions to query Salesforce CRM directly rather than relying on Data Cloud profiles.

🧪 Testing & Deployment

Agent Testing Center

The built-in Agent Testing Center (available in Setup → Agentforce → Agents) provides a conversational sandbox where you can:

  • Simulate multi-turn conversations against your agent configuration.
  • Inspect the full reasoning trace: which Topic was matched, which Actions were called, what inputs/outputs were passed, and the final LLM prompt (masked).
  • Test edge cases: ambiguous inputs, off-topic requests, escalation triggers.
  • Compare responses across different instruction variations without redeploying.

Deployment Channels

  • Messaging for In-App & Web: Embed the agent in your website or mobile app via the Embedded Service SDK. Supports SSO via Experience Cloud.
  • Experience Cloud Sites: Deploy agents directly in portal/community sites with data scoped to the authenticated user's profile.
  • Salesforce Service Cloud (Live Agent): Agents handle initial triage — escalate to human agents in the Service Console when needed, with full conversation context transferred.
  • API access: Call Agentforce agents programmatically via the Agent API, enabling integration with custom apps, IVR systems, or third-party platforms.

Monitoring & Iteration

  • Use the Einstein Activity Tracker to review production conversations — identify where agents are failing to route correctly or generating poor responses.
  • Monitor Escalation Rate as your primary quality metric — high escalation rates indicate Topics are not covering user needs adequately.
  • Review Topic Misclassification events: cases where the agent matched the wrong Topic. Refine Topic descriptions and instructions accordingly.
  • Use A/B testing via Agentforce's configuration versioning to compare instruction variants in production with controlled traffic splits.
