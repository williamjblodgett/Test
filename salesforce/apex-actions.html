💻 @InvocableMethod Basics

The @InvocableMethod annotation marks a static Apex method as invocable — callable from Flow, Process Builder, and Agentforce agents. It is the gateway for custom Apex logic to participate in the Salesforce declarative platform.

Basic Annotation Structure

public class MyAction {

    @InvocableMethod(
        label='My Action Label'
        description='Clear description of what this action does and when to use it. The LLM reads this.'
        category='My Category'
    )
    public static List<OutputClass> execute(List<InputClass> inputs) {
        List<OutputClass> results = new List<OutputClass>();
        for (InputClass input : inputs) {
            OutputClass output = new OutputClass();
            // Your logic here
            results.add(output);
        }
        return results;
    }
}

Key Rules

  • The class must be public or global.
  • The method must be static.
  • The method must accept a List parameter and return a List. This is the bulkification contract — even if you only process one item at a time.
  • The annotation's label is what appears in the UI. The description is what the LLM reads to decide when to invoke the action.
  • Write the description as a clear, precise sentence: "Retrieves the current order status and estimated delivery date for a given order number."
💡 The description is the most important part. A crystal-clear description with a mediocre implementation often performs better than a perfect implementation with a vague description.

📦 Input/Output Variable Types

Input and output data is passed via inner classes annotated with @InvocableVariable:

@InvocableVariable Annotation

public class InputClass {
    @InvocableVariable(
        label='Customer Email Address'
        description='The email address of the customer to look up. Use the email from the conversation context.'
        required=true
    )
    public String customerEmail;

    @InvocableVariable(
        label='Include Order History'
        description='Set to true to include the last 5 orders in the response.'
        required=false
    )
    public Boolean includeOrders = false;
}

Supported Variable Types

  • Primitives: String, Integer, Long, Double, Boolean, Date, Datetime, Decimal, ID
  • SObject types: Any Salesforce standard or custom object (e.g., Contact, Case__c)
  • List of primitives: List<String>, List<Integer>
  • List of SObjects: List<Contact>
  • Apex-Defined types: Custom classes decorated with @AuraEnabled

Required vs. Optional Variables

Mark variables as required=true for data the agent must provide. Required variables will prevent the action from appearing in agent action selection if the data can't be provided. Optional variables default to null if not provided — always null-check optional inputs in your implementation.

🚀 Your First Apex Action for an Agent

A complete, minimal Apex action that looks up a customer by email and returns key account info:

public class GetCustomerInfoAction {

    @InvocableMethod(
        label='Get Customer Info by Email'
        description='Retrieves the customer name, account name, account tier, and number of open cases for a customer identified by email address. Use when you need to identify the customer before personalizing a response.'
    )
    public static List<Result> execute(List<Request> requests) {
        List<Result> results = new List<Result>();

        for (Request req : requests) {
            Result res = new Result();

            List<Contact> contacts = [
                SELECT Id, Name, AccountId,
                       Account.Name, Account.Type,
                       (SELECT Id FROM Cases WHERE Status != 'Closed' LIMIT 5)
                FROM Contact
                WHERE Email = :req.customerEmail
                LIMIT 1
            ];

            if (contacts.isEmpty()) {
                res.found = false;
                res.message = 'No customer found with that email address.';
            } else {
                Contact c = contacts[0];
                res.found = true;
                res.customerName = c.Name;
                res.accountName = c.Account.Name;
                res.accountTier = c.Account.Type;
                res.openCaseCount = c.Cases.size();
                res.message = 'Customer found: ' + c.Name + ' at ' + c.Account.Name;
            }

            results.add(res);
        }

        return results;
    }

    public class Request {
        @InvocableVariable(label='Customer Email' required=true
            description='Email address of the customer to look up.')
        public String customerEmail;
    }

    public class Result {
        @InvocableVariable public Boolean found;
        @InvocableVariable public String customerName;
        @InvocableVariable public String accountName;
        @InvocableVariable public String accountTier;
        @InvocableVariable public Integer openCaseCount;
        @InvocableVariable public String message;
    }
}

Adding to Agent Builder

  1. Save and deploy the Apex class to your Salesforce org.
  2. In Agent Builder → Topic → Add Action → Select "Apex Action".
  3. Search for "Get Customer Info by Email" — it will appear if the class is deployed and active.
  4. Review the auto-populated input/output variables and add an action description for the agent context.

🔍 SOQL Patterns for Agent Actions

Relationship Queries

Fetch parent and child data in a single query to minimize SOQL count:

// Parent traversal (child → parent)
Contact c = [
    SELECT Name, Email,
           Account.Name, Account.Type, Account.AnnualRevenue,
           Account.Owner.Name
    FROM Contact WHERE Id = :contactId LIMIT 1
];

// Child subquery (parent → children)
Account acc = [
    SELECT Name, Type,
           (SELECT Id, Subject, Status FROM Cases
            WHERE Status != 'Closed' ORDER BY CreatedDate DESC LIMIT 5),
           (SELECT Id, Name, Amount, StageName FROM Opportunities
            WHERE IsClosed = false ORDER BY CloseDate ASC LIMIT 3)
    FROM Account WHERE Id = :accountId LIMIT 1
];

Dynamic SOQL for Agent-Extracted Values

When the agent extracts user input (e.g., a search term), use bind variables — never string concatenation:

// ✅ Safe — bind variable
String searchTerm = '%' + req.productName + '%';
List<Product2> products = [
    SELECT Name, Description, ProductCode
    FROM Product2
    WHERE Name LIKE :searchTerm AND IsActive = true
    LIMIT 10
];

// ❌ DANGEROUS — string concatenation = SOQL injection risk
String query = 'SELECT Name FROM Product2 WHERE Name LIKE \'%'
               + req.productName + '%\''; // NEVER DO THIS

Null-Safe Field Access

Queried records may have null fields. Always null-check before accessing:

res.phoneNumber = (c.Phone != null) ? c.Phone : 'Not on file';
res.accountName = (c.Account != null) ? c.Account.Name : 'No account';

🌐 External Callouts from Apex Actions

Apex actions can call external HTTP APIs — ERP systems, logistics providers, payment processors, ticketing systems. Use Named Credentials for authentication.

Basic HTTP Callout Pattern

public class CheckInventoryAction {

    @InvocableMethod(
        label='Check Product Inventory'
        description='Checks real-time inventory levels for a product SKU from the ERP system.'
    )
    public static List<InventoryResult> execute(List<InventoryRequest> requests) {
        List<InventoryResult> results = new List<InventoryResult>();

        for (InventoryRequest req : requests) {
            InventoryResult res = new InventoryResult();
            try {
                HttpRequest httpReq = new HttpRequest();
                // Named Credential — credentials are never in code
                httpReq.setEndpoint('callout:ERP_System/api/inventory/' + req.productSku);
                httpReq.setMethod('GET');
                httpReq.setHeader('Content-Type', 'application/json');
                httpReq.setTimeout(10000); // 10 second timeout

                Http http = new Http();
                HttpResponse httpRes = http.send(httpReq);

                if (httpRes.getStatusCode() == 200) {
                    Map<String, Object> body = (Map<String, Object>)
                        JSON.deserializeUntyped(httpRes.getBody());
                    res.quantityAvailable = (Integer) body.get('quantity');
                    res.warehouse = (String) body.get('warehouse');
                    res.success = true;
                } else {
                    res.success = false;
                    res.errorMessage = 'ERP returned status ' + httpRes.getStatusCode();
                }
            } catch (Exception e) {
                res.success = false;
                res.errorMessage = 'Could not reach inventory system. Please try again.';
            }
            results.add(res);
        }
        return results;
    }

    public class InventoryRequest {
        @InvocableVariable(label='Product SKU' required=true) public String productSku;
    }
    public class InventoryResult {
        @InvocableVariable public Boolean success;
        @InvocableVariable public Integer quantityAvailable;
        @InvocableVariable public String warehouse;
        @InvocableVariable public String errorMessage;
    }
}
⚠️ Callouts cannot be made in the same transaction as DML operations unless the callout happens before the DML. Structure your agent action flows to call external APIs before making any Salesforce record changes.

⚠️ Error Handling in Apex Actions

Unhandled exceptions in Apex actions cause the agent to throw a generic error and often trigger an escalation. Always catch and handle exceptions explicitly.

Try-Catch Pattern

try {
    // Business logic here
    res.success = true;
} catch (QueryException qe) {
    // Specific: record not found, too many rows, etc.
    res.success = false;
    res.userMessage = 'I couldn\'t find that record. Please check the details and try again.';
    logError('QueryException in GetOrderAction', qe.getMessage(), req.orderId);
} catch (CalloutException ce) {
    // Specific: external API unreachable
    res.success = false;
    res.userMessage = 'I\'m having trouble reaching the external system. Please try again in a moment.';
    logError('CalloutException in GetOrderAction', ce.getMessage(), null);
} catch (Exception e) {
    // Generic fallback
    res.success = false;
    res.userMessage = 'Something went wrong. Please try again or contact support.';
    logError('UnexpectedException in GetOrderAction', e.getMessage(), null);
}

User-Facing vs. Technical Error Messages

  • The userMessage output variable is what the agent relays to the customer — write it empathetically, without technical details.
  • Log the technical error message (exception class, message, stack trace) to a custom ErrorLog__c object for engineering review.
  • Never expose SOQL error messages or Apex stack traces in agent responses.

✏️ DML Best Practices in Agent Actions

DML operations (insert, update, delete, upsert) in Apex actions modify Salesforce data. This is powerful but requires careful handling.

Confirmation Before Destructive Operations

For actions that modify or delete data, design your agent topic with a confirmation step. In the topic instructions: "Before executing the Cancel Order action, confirm with the customer: 'I'm about to cancel order [order number]. Please confirm you want to proceed.'" Only proceed after explicit confirmation.

DML Error Handling

try {
    // Database.insert with allOrNothing = false allows partial success
    List<Database.SaveResult> saveResults =
        Database.insert(recordsToCreate, false);

    Integer successCount = 0;
    for (Database.SaveResult sr : saveResults) {
        if (sr.isSuccess()) successCount++;
        else {
            for (Database.Error err : sr.getErrors()) {
                // Log each individual record error
                System.debug('DML Error: ' + err.getMessage()
                    + ' Fields: ' + err.getFields());
            }
        }
    }
    res.recordsCreated = successCount;
    res.success = (successCount > 0);
} catch (DmlException de) {
    res.success = false;
    res.userMessage = 'I wasn\'t able to complete that change. Please try again.';
}

🧪 Testing Apex Actions

@isTest
public class GetCustomerInfoActionTest {

    @TestSetup
    static void setup() {
        Account acc = new Account(Name='Test Corp', Type='Enterprise');
        insert acc;

        Contact con = new Contact(
            FirstName='Test', LastName='User',
            Email='test@example.com', AccountId=acc.Id
        );
        insert con;

        Case c = new Case(ContactId=con.Id, Status='Open', Subject='Test Issue');
        insert c;
    }

    @isTest
    static void testCustomerFound() {
        GetCustomerInfoAction.Request req = new GetCustomerInfoAction.Request();
        req.customerEmail = 'test@example.com';

        Test.startTest();
        List<GetCustomerInfoAction.Result> results =
            GetCustomerInfoAction.execute(new List<GetCustomerInfoAction.Request>{req});
        Test.stopTest();

        System.assertEquals(1, results.size());
        System.assertEquals(true, results[0].found);
        System.assertEquals('Test Corp', results[0].accountName);
        System.assertEquals('Enterprise', results[0].accountTier);
        System.assertEquals(1, results[0].openCaseCount);
    }

    @isTest
    static void testCustomerNotFound() {
        GetCustomerInfoAction.Request req = new GetCustomerInfoAction.Request();
        req.customerEmail = 'notfound@nowhere.com';

        Test.startTest();
        List<GetCustomerInfoAction.Result> results =
            GetCustomerInfoAction.execute(new List<GetCustomerInfoAction.Request>{req});
        Test.stopTest();

        System.assertEquals(false, results[0].found);
    }
}

⚡ Async Patterns for Agent Actions

Some operations are too slow or resource-intensive for a synchronous agent action. Use async Apex to fire long-running processes and return immediately.

Queueable Apex Pattern

// The agent action — synchronous, returns immediately
@InvocableMethod(
    label='Trigger Refund Processing'
    description='Initiates an asynchronous refund process for an order. Returns a job ID immediately.'
)
public static List<RefundResult> triggerRefund(List<RefundRequest> requests) {
    List<RefundResult> results = new List<RefundResult>();
    for (RefundRequest req : requests) {
        // Enqueue async job and return job ID
        ID jobId = System.enqueueJob(new RefundProcessor(req.orderId, req.amount));
        RefundResult res = new RefundResult();
        res.jobId = jobId;
        res.message = 'Refund is being processed. Reference ID: ' + jobId
                    + '. You will receive a confirmation email within 24 hours.';
        results.add(res);
    }
    return results;
}

// The async processor
public class RefundProcessor implements Queueable, Database.AllowsCallouts {
    private String orderId;
    private Decimal amount;

    public RefundProcessor(String orderId, Decimal amount) {
        this.orderId = orderId;
        this.amount = amount;
    }

    public void execute(QueueableContext ctx) {
        // Long-running refund logic here
        // Can make callouts (Database.AllowsCallouts)
        // Has higher limits than synchronous execution
    }
}

When to Use Async

  • Operations that take more than 3–5 seconds (will cause visible agent latency)
  • Operations that make multiple sequential external API calls
  • Large batch DML operations (thousands of records)
  • Operations that require elevated governor limits (Queueable has higher CPU and SOQL limits)

📦 Bulk Invocable Handling

Although agents typically call actions with a single input, the invocable contract requires List parameters for bulkification. Properly bulkified actions are more efficient and reusable.

True Bulk Pattern

public static List<Result> execute(List<Request> requests) {
    // Step 1: Collect all input values
    Set<String> allOrderIds = new Set<String>();
    for (Request req : requests) {
        allOrderIds.add(req.orderId);
    }

    // Step 2: ONE query for all inputs (not one query per input)
    Map<String, Order> orderMap = new Map<String, Order>();
    for (Order o : [SELECT Id, OrderNumber, Status, ShipDate
                    FROM Order WHERE Id IN :allOrderIds]) {
        orderMap.put(o.Id, o);
    }

    // Step 3: Map results back to requests
    List<Result> results = new List<Result>();
    for (Request req : requests) {
        Result res = new Result();
        Order o = orderMap.get(req.orderId);
        if (o != null) {
            res.found = true;
            res.status = o.Status;
        } else {
            res.found = false;
        }
        results.add(res);
    }
    return results;
}

🗄️ Platform Cache for Agent Performance

Platform Cache is Salesforce's in-memory key-value store. For agent actions that repeatedly query the same reference data, caching reduces latency and SOQL consumption dramatically.

Session vs. Org Cache

  • Session Cache: Scoped to a specific user session. Data expires with the session. Use for: user-specific data that changes rarely during a session (e.g., user preferences, authenticated customer profile).
  • Org Cache: Shared across all sessions in the org. Use for: configuration data, reference tables, product catalog, policy documents that are the same for all users.

Cache-Aside Pattern for Agent Actions

public static List<Result> execute(List<Request> requests) {
    String cacheKey = 'local.ProductCache.' + requests[0].productCode;
    Cache.OrgPartition orgCache = Cache.Org.getPartition('local.ProductCache');

    Product2 product = (Product2) orgCache.get(cacheKey);

    if (product == null) {
        // Cache miss — query the database
        product = [SELECT Name, Description, Price__c
                   FROM Product2 WHERE ProductCode = :requests[0].productCode LIMIT 1];
        // Cache for 1 hour (3600 seconds)
        orgCache.put(cacheKey, product, 3600);
    }
    // Use product...
}

Cache Invalidation

Cache entries expire automatically after the configured TTL. For data that changes on a schedule (e.g., pricing updates at midnight), set the TTL to match the update frequency. For data that can change at any time (e.g., stock levels), either use a very short TTL or trigger cache invalidation from your record-triggered flows when the source data changes.

📊 Governor Limit Strategies

Monitoring Limit Consumption

// Add to your action for debugging/monitoring
System.debug('SOQL queries used: ' + Limits.getQueries()
    + ' / ' + Limits.getLimitQueries());
System.debug('CPU time used: ' + Limits.getCpuTime()
    + 'ms / ' + Limits.getLimitCpuTime() + 'ms');
System.debug('DML rows used: ' + Limits.getDmlRows()
    + ' / ' + Limits.getLimitDmlRows());

Limit-Safe Design Patterns

  • SOQL limit: Use parent-child relationship queries to fetch related data in one query. Use Platform Cache for repeated lookups. Use aggregate SOQL instead of iterating records for counts/sums.
  • CPU limit: Offload heavy computation to Queueable or Batch Apex. Avoid complex string manipulation in loops. Pre-sort data in SOQL using ORDER BY instead of in code.
  • DML limit: Always collect records in a list and DML the list once (never DML inside a loop). Use upsert for create-or-update scenarios instead of separate insert/update.
  • Heap size: Don't keep large result sets in memory longer than needed. Process and discard records within the loop rather than accumulating them all first.

🧪 Mock HTTP Callout Testing

Apex tests cannot make real HTTP callouts. Use the HttpCalloutMock interface to mock external API responses in your tests.

// Mock implementation
public class MockInventoryAPI implements HttpCalloutMock {
    private Integer statusCode;
    private String responseBody;

    public MockInventoryAPI(Integer code, String body) {
        this.statusCode = code;
        this.responseBody = body;
    }

    public HttpResponse respond(HttpRequest req) {
        HttpResponse res = new HttpResponse();
        res.setStatusCode(statusCode);
        res.setBody(responseBody);
        res.setHeader('Content-Type', 'application/json');
        return res;
    }
}

// Test class
@isTest
public class CheckInventoryActionTest {

    @isTest
    static void testSuccessResponse() {
        String mockBody = '{"quantity": 150, "warehouse": "WEST-01"}';
        Test.setMock(HttpCalloutMock.class, new MockInventoryAPI(200, mockBody));

        CheckInventoryAction.InventoryRequest req = new CheckInventoryAction.InventoryRequest();
        req.productSku = 'SKU-001';

        Test.startTest();
        List<CheckInventoryAction.InventoryResult> results =
            CheckInventoryAction.execute(
                new List<CheckInventoryAction.InventoryRequest>{req}
            );
        Test.stopTest();

        System.assertEquals(true, results[0].success);
        System.assertEquals(150, results[0].quantityAvailable);
        System.assertEquals('WEST-01', results[0].warehouse);
    }

    @isTest
    static void testApiError() {
        Test.setMock(HttpCalloutMock.class, new MockInventoryAPI(503, ''));

        CheckInventoryAction.InventoryRequest req = new CheckInventoryAction.InventoryRequest();
        req.productSku = 'SKU-999';

        Test.startTest();
        List<CheckInventoryAction.InventoryResult> results =
            CheckInventoryAction.execute(
                new List<CheckInventoryAction.InventoryRequest>{req}
            );
        Test.stopTest();

        System.assertEquals(false, results[0].success);
        System.assertNotEquals(null, results[0].errorMessage);
    }
}

🏗️ Composite Actions

A composite action fetches data from multiple sources and returns a single rich result object — reducing the number of agent iterations needed per turn.

When to Build a Composite Action

  • The agent consistently needs 3+ pieces of data before it can respond, currently requiring 3 separate action calls
  • You want to reduce agent latency by parallelizing data fetches (fetch from Salesforce and an external API simultaneously)
  • The combined result provides context that's more useful than the individual parts (e.g., order + customer profile + open cases = complete service context)

Parallelizing Data Fetches

Standard Apex executes synchronously — you can't truly parallelize within a single transaction. However, you can minimize round trips by batching all SOQL queries before processing:

// Fetch everything you need upfront — don't query in sequence
Contact contact = [SELECT Id, Name, AccountId, Account.Name, Account.Type
                   FROM Contact WHERE Email = :req.email LIMIT 1];

// Now use contact.AccountId in a second query
List<Order> recentOrders = [SELECT Id, OrderNumber, Status, TotalAmount
                              FROM Order WHERE AccountId = :contact.AccountId
                              ORDER BY CreatedDate DESC LIMIT 5];

List<Case> openCases = [SELECT Id, CaseNumber, Subject, Status
                         FROM Case WHERE AccountId = :contact.AccountId
                         AND Status != 'Closed' ORDER BY CreatedDate DESC LIMIT 3];

// Assemble composite result
res.customerName = contact.Name;
res.accountName = contact.Account.Name;
res.recentOrderCount = recentOrders.size();
res.openCaseCount = openCases.size();
// ... build formatted summary string
