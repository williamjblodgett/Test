⚡ Introduction to Flow Builder

Salesforce Flow Builder is a visual tool for building automated workflows — no code required. Flows are the primary way Agentforce actions interact with Salesforce data: looking up records, creating cases, updating accounts, sending emails, and calling external APIs.

For Agentforce specifically, you'll primarily build Autolaunched Flows — background processes that run server-side when an agent calls them as an action. Understanding Flow Builder is essential for anyone building real-world Agentforce implementations.

💡 Even if you're a developer who would naturally reach for Apex, start with Flow for agent actions — Flow is easier to test, debug, and maintain, and it's what Salesforce recommends as the default action type.

📋 Flow Types

Salesforce offers several flow types, each designed for different trigger models:

Flow TypeTriggered ByAgentforce Compatible?
Autolaunched Flow (No Trigger)Invoked programmatically (Apex, other flows, agents)✓ Yes — primary type
Record-Triggered FlowRecord create/update/delete in Salesforce✗ No
Screen FlowLaunched by a user who interacts with UI screens✗ No
Scheduled FlowRuns on a time schedule✗ No
Platform Event–Triggered FlowA Platform Event message is published✗ (indirect use)
⚠️ Common mistake: Agents only work with Autolaunched Flows (No Trigger). A Screen Flow will never appear as an available action in Agent Builder — even if it's well-built and perfectly functional.

🧩 Core Flow Elements

Flow Builder provides a palette of elements that you connect together visually. Here are the most important ones for agent actions:

Data Elements

  • Get Records: Query Salesforce records using filter criteria. Returns one or many records (your choice). The most commonly used element in agent flows.
  • Create Records: Create one or more new Salesforce records. Returns the ID of the created record.
  • Update Records: Update one or more existing records that match criteria.
  • Delete Records: Delete records matching criteria. Use carefully — this is irreversible.

Logic Elements

  • Decision: Branch your flow based on conditions (like an if/else statement). Each branch is a separate path through the flow.
  • Assignment: Set or update a variable's value. Used to build up results, concatenate strings, or initialize counters.
  • Loop: Iterate over a collection of records or values, performing operations on each item.

Action Elements

  • Action: Call an Apex @InvocableMethod, a quick action, a flow action, or a named credential external service.
  • Subflow: Call another Flow from within your flow — excellent for modular design.
  • Send Email: Send an email using a configured email template or free-form text.

🚀 Your First Autolaunched Flow for an Agent

Let's build a "Get Order Status" flow that an Agentforce action can call.

Step 1 — Create the Flow

  1. Navigate to Setup → Flows → New Flow.
  2. Select Autolaunched Flow (No Trigger).
  3. Click Create.

Step 2 — Add Input Variables

In the left panel, click Manager → New Resource → Variable:

  • API Name: inputOrderNumber
  • Data Type: Text
  • Available for Input: ✓ (checked)
  • Available for Output: unchecked
  • Description: "The order number provided by the customer"

Step 3 — Add a Get Records Element

Drag a Get Records element onto the canvas and connect it from Start:

  • Object: Order
  • Filter: OrderNumber equals {!inputOrderNumber}
  • How many records: Only the first record
  • Store record data: Choose fields and assign to variables
  • Assign output fields to: create output variables for Status, ShipmentTrackingNumber, DeliveryDate

Step 4 — Add a Decision Element

Add a Decision to check if a record was found:

  • Outcome 1: "Order Found" — condition: {!Get_Order.Id} is null = False
  • Default Outcome: "Order Not Found"

Step 5 — Add Output Variables

Create output variables (Available for Output: ✓):

  • outputOrderStatus (Text) — set via Assignment element to {!Get_Order.Status}
  • outputFound (Boolean) — set to True in the "Order Found" path, False in "Not Found"
  • outputMessage (Text) — set to a human-readable message in each path

Step 6 — Save and Activate

Save the flow with a clear name ("Get Order Status for Agent") and click Activate. Active autolaunched flows are available as actions in Agent Builder.

📦 Variables & Resources

Variables are the containers that store data as your flow runs. Getting variable configuration right is critical for agent flows.

Variable types available in Flow

  • Text: String values — names, messages, IDs, URLs
  • Number: Integer or decimal values
  • Currency: Monetary amounts with currency formatting
  • Date / Date/Time: Date and timestamp values
  • Boolean: True/false flags
  • Record: A single Salesforce record of a specific object type
  • Record Collection: A list of Salesforce records of a specific type
  • Apex-Defined: Complex types defined by an Apex class (advanced)

Input vs. Output Variables

For agent actions, this distinction is critical:

  • Available for Input = true: The Atlas Reasoning Engine can pass a value into this variable from the conversation context. These are the parameters the agent must provide to run the flow.
  • Available for Output = true: The flow returns this variable's value back to the agent after execution. The agent uses output values in its response.
💡 Naming matters: Variable names and descriptions are used by the LLM to understand what to pass in and what to expect back. Use clear, descriptive names like customerEmailAddress instead of var1.

🤖 Designing Flows Specifically for Agentforce

Agent-facing flows have unique design considerations vs. general Salesforce automation. The agent's reasoning engine is the "user" of your flow — design with that in mind.

Keep Each Action Focused

Unlike human-facing flows that might do 10 things in sequence, agent flows should do one thing well. The agent reasons about which action to invoke — give it composable, single-purpose tools rather than monolithic mega-flows. Example: separate flows for "Get Order Status", "Create Return Request", and "Send Tracking Link" — not one flow that does all three based on parameters.

Explicit Success/Failure Output

Always include a boolean outputSuccess and a text outputMessage in every agent flow. The agent uses these to determine how to respond:

  • Success = false + message = "No order found for that number" → agent reports the issue to the user
  • Success = true + message = "Order found: status is In Transit" → agent uses the structured data to form a response

Without explicit success indicators, the agent has to infer success from the presence/absence of data — which can lead to confusing responses when data is legitimately empty.

Well-Described Input Variables

The LLM maps conversation data to your flow's input variables by reading their names and descriptions. For each input variable:

  • API Name: camelCase, descriptive (e.g., customerOrderNumber)
  • Description: Plain English explanation of what value is expected, including format if relevant (e.g., "The customer's order number in format ORD-XXXXXX. Ask the customer for this if not provided.")

Action Description in Agent Builder

When you add a Flow as an action in Agent Builder, write a clear action description. This is separate from the flow's own label. The action description is what the Atlas Reasoning Engine reads to decide when to invoke this action. Example: "Use this action to retrieve the current status, shipping carrier, and estimated delivery date for a customer order. Requires an order number."

📚 Collections & Loops

Many agent scenarios require processing multiple records — a customer's open cases, recent orders, or product recommendations. Understanding collections and loops in Flow is essential.

Get Records with Multiple Records

When you configure a Get Records element to retrieve "All records", the output is a Record Collection — a list of records. You can then iterate over this list with a Loop element.

Using Loop Elements

  1. Add a Loop element, set the collection to your Record Collection variable.
  2. Each iteration, the current record is available as a Loop Variable (a single record of the same type).
  3. Inside the loop, add logic to process each record — check conditions, accumulate data, or build output strings.
  4. Use an Assignment element to append to a Text Variable with each iteration, building up a formatted summary string.

Practical Example: Summarize Open Cases

Input: customerAccountId (Text)
Get Records: Cases WHERE AccountId = {!customerAccountId}
             AND Status != 'Closed' → casesCollection
Loop over casesCollection:
  Assignment: outputSummary += "• Case " + {!currentCase.CaseNumber}
              + " — " + {!currentCase.Subject}
              + " (" + {!currentCase.Status} + ")\n"
Output: outputSummary (Text), outputCaseCount (Number)

Collection Filtering Without Loops

For simple filtering operations, use the Filter element on a collection instead of a loop with a decision — it's more performant and concise. Available in API version 54.0+.

⚠️ Fault Paths & Error Handling

Every element in a Flow that performs data operations (Get Records, Create Records, Action elements) can fail. Unhandled failures cause the agent to show a generic error message and potentially escalate to a human agent unnecessarily. Good error handling prevents this.

Fault Connectors

Every data or action element has a Fault connector (shown as a red diamond). Connect this to a fault path that:

  1. Sets outputSuccess = false
  2. Sets outputMessage to a user-friendly error description (not a Salesforce error code)
  3. Optionally logs the technical error to a custom log object for debugging

Example Fault Path

  • Fault connector → Assignment element:
    • outputSuccess = false
    • outputMessage = "I wasn't able to retrieve that order right now. Please try again or contact us directly."
    • outputErrorDetail = {!$Flow.FaultMessage} (for logging only — don't show to users)
  • Create Records → ErrorLog__c record with the fault message and timestamp (for ops monitoring)
⚠️ Never expose {!$Flow.FaultMessage} directly to the agent's output — it contains technical Salesforce error codes that are confusing to end users and may expose internal system details.

🧩 Subflows — Modular Design

Subflows let you call one Flow from another. This is the Flow equivalent of a helper function in code — it promotes reuse and keeps individual flows manageable.

When to Use Subflows

  • Logic that appears in multiple agent actions (e.g., "validate and look up a customer by email" is needed in both the Order Status and Account Update flows)
  • A complex operation that would make the parent flow too large to understand visually
  • Shared error logging logic — centralize it in one subflow called from every agent action

Subflow Design Pattern

Build subflows as pure input-output transformers: they take inputs, do work, and return outputs. Avoid flows that have side effects AND return data — separate the query flow from the mutation flow for clarity and safety.

Passing Data Between Parent and Subflow

When adding a Subflow element, you'll see input/output variable mapping. Map your parent flow's variables to the subflow's input variables explicitly. Output variable mapping works the same way in reverse — the parent receives the subflow's outputs back after it completes.

🔀 Complex Decision Logic

The Decision element supports multi-path branching with multiple outcomes. Each outcome has its own set of conditions, all of which must be true for that outcome to be taken.

Condition Operators Available

  • Equals / Does Not Equal
  • Greater Than / Less Than / Greater Than or Equal / Less Than or Equal
  • Contains / Does Not Contain (text)
  • Starts With / Ends With
  • Is Null / Is Changed
  • Includes / Excludes (multi-select picklists)

AND vs. OR Logic

Within a single outcome, conditions can use AND logic (all conditions must be true) or you can configure OR logic. For complex combinations, use formula resources (see below).

Formula Resources

For decision conditions too complex for the standard condition builder, use a Formula resource. Formulas support Salesforce formula syntax — you can build complex Boolean expressions and reference any flow variable. The formula evaluates to a Boolean value that the Decision element can branch on.

🧪 Testing Flows

Debug Mode in Flow Builder

Use the Debug button in Flow Builder (top right) to run your flow with specific test inputs and trace execution step-by-step. The debug trace shows:

  • Which elements executed and in what order
  • Variable values at each step
  • SOQL queries executed and their results
  • Any fault messages from failed elements

Flow Test Cases (Formal Test Suite)

Flow Builder supports a formal test suite. Create test cases for:

  • Happy path: valid input that returns expected output
  • Not found path: input that matches no records — verify the "not found" output variables are set correctly
  • Fault path: test that your fault handling logic activates (you can trigger faults by providing invalid object IDs in DML operations)
  • Edge cases: empty strings, null values, maximum-length inputs

Testing via Agentforce Testing Center

The best end-to-end test is always through the Agent Testing Center — it shows you exactly what inputs the LLM passed to your flow action and what outputs it received back. Review the reasoning trace for every test scenario to confirm input/output mapping is working as intended.

📦 Bulk Processing Patterns

Flow governor limits apply per-transaction — not per-element. When your agent action processes large data sets, you need to design for bulkification.

Governor Limits Relevant to Agent Flows

  • SOQL queries: 100 per transaction
  • DML statements: 150 per transaction
  • Records retrieved: 50,000 per transaction
  • CPU time: 10,000ms (synchronous), 60,000ms (asynchronous)
  • Heap size: 6MB (synchronous), 12MB (asynchronous)

Bulkification in Loops

One of the most common performance mistakes is performing DML inside a loop — creating one record per iteration instead of building a collection and creating all records at once:

❌ BAD: DML inside loop
Loop over orderItems:
  Create Record: OrderLineItem (1 DML per iteration = N DML)

✅ GOOD: Collect then bulk-create
Loop over orderItems:
  Assignment: Add currentItem to newItemsCollection
[After loop]
Create Records: newItemsCollection (1 DML for all)

Pre-Aggregating with SOQL

Instead of fetching 100 records and summing them in a Flow loop, use SOQL aggregate functions in a Get Records element with a custom formula resource or an Apex action. Moving aggregation to the database layer is orders of magnitude faster.

📡 Platform Events in Agent Flows

Platform Events enable real-time, event-driven communication between Salesforce components. In agent flows, they can be used to trigger asynchronous processes or notify other systems that an agent has taken an action.

Publishing a Platform Event from a Flow

Use an Action element with the Platform Event as the target to publish an event from your agent flow:

  • Define a Platform Event object (Setup → Platform Events → New)
  • In your agent flow, add a Create Records element targeting the Platform Event object
  • Populate the event fields with data from your flow variables
  • After saving, any configured Platform Event–Triggered Flows or Apex subscribers will receive the event asynchronously

Use Cases

  • Async processing: Agent creates a return request record and publishes an event. A separate subscriber flow handles complex return logistics asynchronously — outside the agent's response window.
  • Real-time notifications: Agent resolves a case and publishes an event that notifies the account manager via Slack via a subscriber flow.
  • Integration triggers: Agent confirms an order and publishes an event that triggers an ERP integration in a subscriber.
💡 Publishing a Platform Event from an agent flow is synchronous (the flow waits for the publish to succeed) but the processing of the event by subscribers is asynchronous. This is ideal for fire-and-forget operations that don't affect the agent's response.

🚀 Flow Performance Optimization

Indexing Strategy for Get Records

SOQL queries in Flow are subject to the same query optimizer rules as all Salesforce SOQL:

  • Always filter on indexed fields (Id, Name, unique/indexed custom fields, External ID fields, standard indexed fields like Email on Contact)
  • Use LIMIT in Get Records — always limit the number of records fetched to what you actually need
  • Avoid filtering on formula fields, long text area fields, or rich text fields — these are not indexable

Reduce Unnecessary SOQL Calls

  • Fetch all needed fields in a single Get Records element rather than multiple sequential queries
  • Use relationship traversal (e.g., Account.Name on a Contact record) to fetch parent record data in the same query
  • Cache reference data in Platform Cache (via Apex) rather than querying it in every agent turn

Flow Interviews and Context

Each agent action invocation creates a new Flow Interview — a complete execution context. There is no state shared between invocations. This means:

  • You cannot use Flow to maintain state between agent turns (use conversation context variables in your agent configuration instead)
  • Each interview starts fresh — cached data in Platform Cache survives between interviews, making it valuable for frequently accessed reference data

🔧 Apex-Defined Types in Flow

When your flow needs to work with complex data structures that don't map to standard Salesforce objects, Apex-Defined Types allow you to define custom data structures in Apex and use them as Flow variable types.

Defining an Apex Type for Flow

global class ShipmentStatus {
    @AuraEnabled @InvocableVariable
    global String carrier;

    @AuraEnabled @InvocableVariable
    global String trackingNumber;

    @AuraEnabled @InvocableVariable
    global String currentLocation;

    @AuraEnabled @InvocableVariable
    global Date estimatedDelivery;

    @AuraEnabled @InvocableVariable
    global Boolean isDelayed;
}

This type can now be used as a variable type in Flow Builder. It enables Flow actions to return structured objects with multiple properties — cleaner than multiple individual output variables for complex action results.

🧪 Apex Testing for Agent Flows

Flow test cases in Flow Builder are useful but limited. For production-grade testing, use Apex test classes to call your flows programmatically — enabling integration into your CI/CD pipeline.

Calling a Flow from an Apex Test

@isTest
public class GetOrderStatusFlowTest {

    @TestSetup
    static void setup() {
        // Create test Order record
        Order__c testOrder = new Order__c(
            OrderNumber__c = 'ORD-999',
            Status__c = 'In Transit',
            CarrierName__c = 'FedEx'
        );
        insert testOrder;
    }

    @isTest
    static void testOrderFound() {
        Map<String, Object> inputs = new Map<String, Object>{
            'inputOrderNumber' => 'ORD-999'
        };

        Flow.Interview flowInterview =
            Flow.Interview.createInterview('Get_Order_Status_for_Agent', inputs);
        flowInterview.start();

        Boolean success = (Boolean) flowInterview.getVariableValue('outputSuccess');
        String status = (String) flowInterview.getVariableValue('outputOrderStatus');

        System.assertEquals(true, success, 'Expected success=true for existing order');
        System.assertEquals('In Transit', status, 'Expected In Transit status');
    }

    @isTest
    static void testOrderNotFound() {
        Map<String, Object> inputs = new Map<String, Object>{
            'inputOrderNumber' => 'ORD-NOTEXIST'
        };

        Flow.Interview flowInterview =
            Flow.Interview.createInterview('Get_Order_Status_for_Agent', inputs);
        flowInterview.start();

        Boolean success = (Boolean) flowInterview.getVariableValue('outputSuccess');
        System.assertEquals(false, success, 'Expected success=false for missing order');
    }
}
